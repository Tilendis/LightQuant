## R1 多视角研判 + 投票/加权

### 实现

| 环节 | 位置 | 说明 |
| --- | --- | --- |
| 技术面（模型版） | `judgements` 表 `view='tech'`，`prompt_version='tech-v1'`，`model='bi_lstm_feat10'`，`source='local'` | 本地训练好的 BiLSTM，十维量价特征，**不调大模型** |
| 技术面（LLM 解读版） | `view='tech'`，`prompt_version='tech-llm-v1'`，`provider='zhipu'`，`model='glm-4-flash'` | 方向由本地模型决定，**理由由大模型写**，大模型不能改方向 |
| 基本面 | `view='fund'`，`prompt_version='fund-rule-v1'`，`model='valuation_percentile'`，`source='local'` | 估值分位规则版，覆盖 9750（全库标的×日期） |
| 基本面（智能体版） | `prompt_version='fund-agent-v2'`（5475）/ `fund-agent-v3`（585），`provider='deepseek'` | 补了行业、财报事件材料的多轮研判，仅覆盖 600 条测试窗口 |
| 情绪面 | `view='sent'`，`prompt_version='sent-v1'`，`provider='zhipu'` | 当日新闻原文 → 结构化评分，2309 + 11 条 |
| 融合 | `view='fusion'`，`prompt_version='fusion-test-3view'`，`model='rule_weighted'` | 加权融合，4746 条 |
| 投票版 | `prompt_version='fusion-vote-v1'`，`model='rule_vote'` | 多数投票，4850 条 |

**加权机制**：权重在验证集（2024-03-15 ~ 08-07）用三方网格搜索定死，结果 `tech 0.90 / fund 0.00 / sent 0.10`，存在 `docs/calib_weights_3view.json`。融合表生成脚本是 `scripts/fuse_views.py`，回测端读到的是已融合结果，`app/service_backtest.py:279` 对 fusion 视角恒取 `method='weighted'`（再投票就是重复计算）。

**三视角是三个智能体而不是三个标签**，判定标准是三条硬差别：

1. 输入不同：技术面吃 5 日窗口的 OHLCV 派生指标；基本面吃估值分位 + 财报事件 + 行业；情绪面吃当日新闻原文。
2. 判定逻辑独立：一个是本地深度模型、一个是可精确计算的规则、一个是 LLM 抽取打分。
3. 输出契约独立可关闭：每个视角一个 `prompt_version`，少传一个视角，融合表就少一路输入，可以单独跑消融。

### 证据

`judgements` 表 62,783 行，50 只标的，日期 2024-03-15 ~ 2024-12-31。`source` 分布：`live` 49,815 / `offline_rule` 12,968——后者是断网或未配 key 时的规则兜底，界面会标注。

各视角准确率（测试期 2024-08-08 ~ 12-31，`app/data/view_accuracy.json`）：

| 视角 | ACC | 样本 | 强信号 ACC | 样本 |
| --- | --- | --- | --- | --- |
| 技术面 | 0.5252 | 4650 | — | — |
| 基本面 | 0.4940 | 4850 | 0.4936 | 3894 |
| 情绪面 | 0.5054 | 920 | 0.5155 | 776 |
| 融合（0.9/0/0.1） | 0.5237 | 4746 | — | — |

> 注：技术面与融合 ACC 为前视泄漏修复后重跑值（z-score 在 train 段拟合、test 段 transform）。修复前 tech 0.5482 / fusion 0.5440，修复后分别降到 0.5252 / 0.5237。fund 与 sent 视角不涉及标准化，数字不变。

### 现场怎么验

行情研判页选 `万华化学`：K 线图上叠四组散点（▲ 看多 / ▼ 看空，按视角分色），下方「四视角研判报告」表逐视角给出 signal / score / 理由 / `prompt_version` / provider，行尾标签标 `offline_rule` 的那些是离线预计算。

### 必须说清的边界

1. **基本面权重 0.00 是标定结果，不是没做**。三方网格搜索里基本面权重从 0 增到 1，验证集准确率单调下降 5.4pp，所以取 0。正确说法是「系统能判定哪个视角在当前区间不可信，并把权重压下去」，不是「基本面没用」。
2. **基本面 0.4940 不低**：这个样本的次日上涨率只有 47.30%，「永远猜跌」就有 52.70%。0.4940 的真实含义是它比「永远猜跌」低 3.3pp，也就是 IC 接近 0（−0.0112），不是「算错了」。
3. **情绪面 920 条只覆盖 18.97%**（测试期 920 / 4850），其余 81% 由融合层 ffill 外推，且 ffill 没有时间衰减。不能说「情绪面提升了预测能力」——0.2pp 的边际改善远小于标准误 0.71pp。
4. **融合 0.5440 与最强单视角 0.5482 几乎持平**，不能说「融合提升了预测能力」。
5. **LLM 测试期语料污染**：2024-08~12 距今不足一年，多数模型很可能见过这段行情。这个 ACC 只能用于视角间横向比较，不作为有效性证据，`view_accuracy.json` 的 `meta.note` 里已写明。

## R2 止盈止损参数 + 异步回测 + 发布

### 实现

| 环节 | 位置 | 说明 |
| --- | --- | --- |
| 异步执行 | `app/service_backtest.py:19/30` | `ThreadPoolExecutor(max_workers=2)`，不用 Celery——单机演示、纯 CPU、断网可跑 |
| 状态机 | `backtest_tasks.status` CHECK `PENDING/RUNNING/SUCCEEDED/FAILED`，`progress` CHECK `[0,1]` | 进度分档推进：0.05 → 0.30 → 0.55 → 0.90 → 1.0（`service_backtest.py:262/275/282/306/313`） |
| 提交接口 | `POST /api/backtest/tasks`（`app/api.py:436`），`need(user,'author')` | 参数校验在写库之前抛 ValueError，负测试不产生脏数据 |
| 预测来源 | 前端 `#btViews` → 请求体 `views`；校验在 `normalize_params()`（`service_backtest.py:138`） | 融合结论 / 仅技术面 / 仅基本面 / 仅情绪面 / 基本面+情绪面 五选一。此前前端写死 `views = ['fusion']`，界面上只有「加权/投票」，等于预设三视角一定融合，单视角做不了对照回测 |
| 融合方式 | 前端 `#btMethodWrap` → `method` | 只有选「融合结论」才出现；单视角不传 `method`，多视角等权直接用加权和取信号、不读融合表。选了单视角却留着「加权/投票」会让人以为单视角也能投票 |
| 预测版本 | 前端 `#btFusionVerWrap` → 请求体 `fusion_version`；白名单在 `FUSION_VERSIONS`（`service_backtest.py`）与 `normalize_params()` | 三档：`auto`（默认，按起点自动派生）/ `fusion-test-3view`（三视角·test 段，08-08 起）/ `fusion-val-3view`（三视角·val 段）。**只暴露"段"、不暴露"权重"**，语义是一句话：这条曲线读的是哪一段的融合表。库内 12 个融合版本中只放行 5 个长表，12 月那批 agent 版只有 600 行、12-16 起，从 08-08 起跨段会取不全却照样"跑成功"给半截结果，所以不进白名单。`method=vote` 时下拉隐藏且后端强制只认 `fusion-vote-v1`——否则会产出"名叫投票、实读加权"的曲线 |
| 参数校验 | `normalize_params()`（`service_backtest.py:84`） | `take_profit_pct` / `stop_loss_pct` ∈ [0,1)，传 8 被 400 拦下并提示「应为小数（0.08 表示 8%）」 |
| 止盈止损 | `backtest/engine_v2.py:125-126` 读参数，`148-156` 判定与成交 | 0 表示关闭；触发价按买入成本算，成交价再吃一次滑点；**同日两端同时触发按止损优先**（最坏情况） |
| T+1 | `engine_v2.py:8/148/193` 用 `held_days >= 1` | 买入当日不可卖，最早次日 |
| 成本 | `engine_v2.py:118-121` 从 cfg 读 `commission_rate / min_commission / stamp_duty_rate / slippage_rate` | 四项已从接口透传（见下） |
| 不可成交 | `engine_v2.py:143/164/194` 用 `high == low` 近似一字板并跳过 | 只能近似，不等于实现涨跌停规则——这条要写进论文 |
| 发布 | `POST /api/strategies/{sid}/publish`（`api.py:634`），`need(user,'author')` | DRAFT → PUBLISHED，指标从 `summary.json` 读，不复制第二份 |

**费率透传**（此前硬编码，是已修的缺陷）：`DEFAULT_PARAMS`（`service_backtest.py:48`）含四项成本，择时口径默认 `0.0003 / 5.0 / 0.001 / 0.0005`；截面路径滑点默认走 `CROSS_SECTION_SLIPPAGE = 0.0020`（`service_backtest.py:81`），用户显式传值则尊重用户值。校验在两条路径共用的公共段，传 `slippage=8` 会被拦下（否则会一路穿到引擎变成 800% 滑点）。

### 证据

**同一个界面、换预测来源跑出来的两条结果**（2026-11-14 实测，区间 2024-08-08 ~ 12-31，提交后各 2.2 秒跑完）：

| 预测来源 | 止盈/止损 | 累计收益 | 年化 | 夏普 | 成交笔数 | 信息比率 |
| --- | --- | --- | --- | --- | --- | --- |
| 融合结论 · 加权 | 0 / 0 | 9.36% | 27.78% | 2.673 | 733 | −1.240 |
| 仅技术面 | 8% / 5% | 9.7976% | 29.18% | 3.0079 | 1138 | −1.1143 |

第一行与主口径 `fusion-test-3view` 的 `cum 0.09361668908883325 / arr 0.27778168257338565 / sharpe 2.6725252001100186 / trades 733` **逐位一致**——说明界面选「融合结论·加权」跑出来的就是主口径，链路同源，不是另起一套算法。

第二行只是「换预测来源能跑通、能读到指标」的证据。**它不是主结果**：单视角技术面 8%/5% 的止盈止损与主口径的 0/0 不同，两组数字不可横比。

**显式选「预测版本 = fusion-test-3view」再跑一次**（前视泄漏修复后重跑）：`cum 0.09361668908883325 / arr 0.27778168257338565 / sharpe 2.6725252001100186 / trades 733`，与主口径**逐位一致**。

参数层另有 9 组用例（通过 6 / 拒绝 3）：`auto + start=08-08` → 派生 `fusion-test-3view`；`auto + method=vote` → 派生 `fusion-vote-v1`；仅技术面 → 版本被清空为 `None`；**拒绝**未知版本名、**拒绝** `vote` 配加权表、**拒绝** 12 月短表 `fusion-agent-v1`。

`strategies` 表 6 行，全部 `PUBLISHED`：

| 策略 | 口径 | 累计收益 | 夏普 | 最大回撤 |
| --- | --- | --- | --- | --- |
| 技术面强信号 v1 | 单视角-技术面 | 14.15% | 3.446 | 3.51% |
| 融合投票 v1 | 投票（多数决） | 21.07% | 2.297 | 6.60% |
| 融合加权 v2 | 旧权重 0.5/0.25/0.25 | 16.88% | 2.850 | 3.13% |
| 融合投票止盈 v1 | 投票 + 止盈 8% / 止损 5% | 11.89% | 2.027 | 5.22% |
| 融合加权 v3 | 验证集标定 0.9/0/0.1 | 9.36% | 2.673 | 2.78% |
| 截面选股 v1 | 技术面 TOP10 五日轮动 | 53.80% | 3.676 | 5.29% |

**止盈止损真实参与计算**，不是摆设：融合投票止盈那条 `take_profit_exits=206`、`stop_loss_exits=216`，`metrics_json` 里另记 `total_fee=91997.94`。

费率透传的验证方式是真跑一次回测读产物：传 `commission_rate=0.0012 / min_commission=3.0 / stamp_duty_rate=0.002 / slippage_rate=0.003`，轮询到 SUCCEEDED 后读 `summary.json` 的 `config`——四项逐位等于传入值。

### 现场怎么验

策略回测页配参数（区间、top_n、止盈止损、四项费率）→ 提交 → 任务列表里看到 `PENDING → RUNNING → SUCCEEDED` 与进度百分比 → 结果区出净值线、买卖点、红色回撤阴影。报告页「读表口径」卡片会回显本次实际读的融合版本（`config.prompt_version`），现场可以指着它说「这条曲线读的是哪一段的表」。

现场还能顺手演一个联动：融合方式切「投票」→ 预测版本下拉自动收起并提示「投票融合只有一版融合表」；预测来源切「仅技术面」→ 融合方式和版本两个下拉一起收起；策略类型切「截面选股」→ 版本下拉置灰（截面只用技术面分数）。

### 必须说清的边界

1. **止盈止损削掉了收益**：累计 21.07% → 11.89%，回撤 6.60% → 5.22%。不能说「止盈止损提升了策略表现」，只能说它换来了更低的回撤与更多的交易次数（384 → 1139 笔）。
2. **一字板只能近似**，`engine_v2.py:15-17` 自己写明了「不等于实现涨跌停规则」。
3. **涨停买入不可成交、跌停卖出不可成交**没有真实实现，只有 `high == low` 这一条近似。

## R3 订阅策略进行模拟跟单

### 实现

| 环节 | 位置 | 说明 |
| --- | --- | --- |
| 订阅 | `POST /api/subscriptions`（`api.py:696`），`need(user,'investor')` | `subscriptions` 表 UNIQUE(investor_id, strategy_id)，状态 ACTIVE / CANCELLED |
| 跟单账户 | `subscriptions` 创建时同步建 `follow_accounts` | 字段 `initial_nav / current_nav / peak_nav / stop_loss_nav / stop_loss_pct`，**`as_of`（净值推到哪个交易日，NULL=还没推过）**，UNIQUE(subscription_id) |
| 交易日历 | `GET /api/trading-days`（`api.py:803`） | 从 `prices` 取 `DISTINCT date`（195 个交易日，2024-03-15 ~ 2024-12-31）。**不取某一只票的 K 线**——单只票停牌日仍是交易日 |
| 推进一日 | `POST /api/follow-accounts/{aid}/advance`（`api.py:779`），body 留空 | 默认语义是**往前走一个交易日**（`service_risk.step_account()`，`service_risk.py:193`）：按该账户 `as_of` 取下一交易日；`as_of` 为空时落在**该策略净值曲线的第一天**（不是全库第一天，否则会撞「早于策略净值起点」） |
| 指定日期推进 | 同上，body `{"date": "2024-09-13"}` | 幂等：同一日期重复推两次结果完全一致（`advance_account` 从曲线首点重算到 cutoff，不累加）；非交易日直接 400，不会被 cutoff 静默吞成周五 |
| 推到期末 | 同上，body `{"date": "latest"}` | 显式要求才这么做，默认不再是这个行为 |
| 批量推进 | `POST /api/follow-accounts/advance-all`（`api.py:813`），`need(user,'investor','risk')` | 每个在途账户**各自**走一个交易日。不统一推到一个 target：老账户已到期末、新账户还没开始，统一取最新会把落后账户一步拉平，统一取最落后会让已到期末的账户净值倒退 |
| 净值推演 | `service_risk.advance_account()`（`service_risk.py:78`） | 按策略净值曲线等比缩放（从 `rows[0][1]` 重算到 cutoff），同时更新 `current_nav / peak_nav / stop_loss_nav / as_of` |
| 持仓明细 | `GET /api/follow-accounts/{aid}/positions`（`api.py:879`），`need(user,'investor','risk')` | 从策略 `trades.csv` 现算，**移动加权平均成本**（`service_risk.positions()`，`service_risk.py:313`） |
| 取消订阅 | `POST /api/subscriptions/{sid}/cancel`（`api.py:839`），`need(user,'investor')` | 只能取消自己的；账户置 LIQUIDATED，写一条 detail 注明「投资者主动取消订阅（非强平）」 |
| 授权来源校验 | `service_risk.advance_account` 先查 `subscriptions.status` | 此前取消订阅后账户仍能被推进，是已修的缺陷 |
| 前端 | 订阅表「净值截至」列 + 每行「推进一日」+ 工具条「推进全部账户」+ 「系统当前交易日」行 + 「推到该日」「推到期末」快捷按钮 | 页面上**不出现任何写死日期**。原来 `app.js` 里 `body: { date: '2024-12-31' }` 已删除——写死日期的样子像「净值是离线算好摆上来的」 |

**订阅后账户是什么状态**：`as_of` 为 NULL、`current_nav` 等于 `initial_nav`。点一次「推进一日」，`as_of` 从 NULL 走到策略曲线首日（策略 7 是 2024-08-14），净值开始逐日变化；再点一次走到 08-15。这就是「模拟跟单」。

**老账户为什么都有 `as_of`**：迁移时给 `current_nav <> initial_nav` 的账户回填了 `MAX(prices.date)`（2024-12-31）——净值已偏离初始值说明当初确实推过，留空会被当成「还没推过」。

**持仓为什么现算而不存表**：模拟跟单是「用策略净值曲线等比缩放」，持有什么由策略决定。存一份会和 `trades.csv` 形成两个真相来源，改一次回测就两边对不上。

### 必须说清的边界

1. **手工强平必须填原因**，不是可选项——接口要 `handled_by` 和 `reason`，事后复盘时「谁按的、依据什么」比「按了」重要。
2. **只有 risk 角色有强平按钮**。operator 能看账户水位，但 `liquidate` 接口只对 risk 开放，给他放个按不动的按钮等于误导。
3. **规则层命中就不调 LLM**，这是设计选择（省 token、结果可复现），不是缺陷。但因此 `llm_verdict` 在规则命中的记录里是空的。
4. **断网时审核降级**：只走规则层，`detail` 写「仅规则层（LLM 调用失败（ProxyError））」，`llm_verdict` 存失败原因。已实测（`docs/工程化收尾说明.md` 第七节）。
5. **后台定时巡检**：lifespan 起 daemon 线程每 30 秒只读一遍所有账户水位（`inspect_all` dry-run，不推进、不写事件），结果缓存在内存。风控页进页即见"自动巡检时间"，不再现算。仍无行情轮询——离线数据切片不需要常驻调度，但后台巡检线程已挂。
6. **汇总的日期口径不是账户真实 `as_of`**。它由 `inspect_all` 按曲线末端（或复盘日期）算出来，所以文案写「按曲线末端水位」，不写具体日期，避免和订阅页「净值截至」的列对不上。
7. **峰值抬升可能让同一账户再出一条预警**。去重键是 `(account_id, kind, date)`，date 取本次重算的 `first_call`；峰值抬高会让早期回撤点变浅、`first_call` 后移到新日期，从而插出第二条。这条记录的是「历史上又一次触及强平线」，不是重复写；同一 `peak` 下反复扫同一天不会重复。

## 审核时大概率会被问的三个点

**问：三个视角是三个智能体，还是同一段提示词换名字？**
答：三条硬差别——输入数据不同（量价指标 / 估值财报事件 / 新闻原文）、判定逻辑独立（本地深度模型 / 可精确计算的规则 / LLM 抽取）、输出契约可单独关闭（每个视角一个 `prompt_version`，可单独跑消融）。且两家 provider：技术面解读与情绪面走智谱，基本面智能体与发帖审核走 DeepSeek / 阿里百炼。

**问：基本面权重为什么是 0？**
答：验证集三方网格搜索的结果，权重从 0 增到 1 验证集准确率单调下降 5.4pp。这是「系统能判定哪个视角当前不可信」，不是「基本面没用」。另一方面，基本面在这个系统里承担的是排雷而不是择时——财务状态是状态量，T+1 涨跌是变化率，两者没有必然因果。

**问：融合到底有没有用？**
答：融合 ACC 0.5237，最强单视角 0.5252，基本持平；策略层主口径 9.36% 跑输基准 19.04%（前视泄漏修复后重跑值），IR 为负（−1.240）。这三条都得自己先说，不能等评审问。系统的价值不在「融合更好」，在于三视角可以各自独立跑、独立评估、独立关闭，能看出哪个视角在这段行情里失效。

> **前视泄漏修复说明**：技术面特征的 z-score 标准化原在 test 段整段拟合（8 月特征减掉了含 12 月分布的均值），已改为只在 train 段拟合、test 段 transform。修复后 tech ACC 从 0.548 降到 0.525，主口径累计收益从 15.97% 降到 9.36%。数字变差但口径可辩护——mean/std 来源可答"train 段"。
