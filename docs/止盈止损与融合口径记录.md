## 1. 纠正：投票与加权机制是生效的

### 1.1 旧判定错在哪

上一轮依据是 `backtest_tasks` 里 `api_2_1`、`api_f_w`、`api_fusion_vote`、`api_fusion_default` 四份指标完全相同，于是判"`method` / `weights` 参数没被使用"。

复核配置后发现：任务 #4/#5/#6 是**三个 tag、同一份配置**——

```
views = ["fusion"]，fusion_version = "fusion-v1"，method = weighted，score_th = 0.0
```

同配置必然同结果。拿三条同配置任务去证明"换 method 没变化"，等于用同一个实验做了三次对照。**这是对照设计错误，不是系统缺陷。**

### 1.2 真正对比投票与加权的一组

| 任务 | tag | 读的融合表 | method | 累计收益 | 夏普 | 最大回撤 | 成交笔数 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| #7 | `api_f_v` | `fusion-vote-v1` | vote | 21.07% | 2.297 | 6.60% | 384 |
| #8 | `api_2_1` | `fusion-v1` | weighted | 16.88% | 2.850 | 3.13% | 523 |

指标完全不同（收益差 4.19pp、笔数差 139 笔），机制生效。

### 1.3 机制的真实位置（答辩必须讲清）

投票/加权**发生在融合表生成阶段**，不在回测阶段：

- `fusion-vote-v1` 存的是"三视角按票数合并"后的分数；
- `fusion-v1` / `fusion-val-v1` 存的是"三视角按标定权重加权"后的分数；
- 回测端对 `fusion` 视角的 `method` 固定为 `weighted`（见 `app/service_backtest.py` 中 `method = "weighted" if "fusion" in params["views"]`），因为它读到的已经是融合结果，再投一次票就是重复计算。

所以"投票还是加权"由**读哪张表**决定，不是由回测参数决定。这也解释了为什么 `api_fv_tp`（命令行传 `method=vote`）与界面任务（后端记 `weighted`）读到同一个 `fusion-vote-v1` 后指标完全一致——`method` 在 fusion 路径上不参与计算。

界面上"读表口径"卡片为此而加，写明"权重在融合阶段固化（回测不重复加权）"。

## 2. 缺陷一：界面百分数直接进引擎，止盈止损永不触发

### 2.1 现象

`index.html` 的输入框标注是"止盈%"、"止损%"，用户填 `8` 表示 8%。`app.js` 原样把 `8` 传给后端，`engine_v2.py` 按小数解释：

```python
tp_px = entry_px * (1 + tp_pct)     # 8 → 成本 × 9，即 900% 止盈
sl_px = entry_px * (1 - sl_pct)     # 5 → 成本 × (-4)，负价，等于永不止损
```

后果是**静默失败**：回测照常跑完、页面照常出数、自检 7 项照常通过，只是止盈止损一次都不会触发。这正是三条早期策略 `take_profit_pct` 全为 0 之外，"想配也配不成"的那条路径。

### 2.2 修复

- `app.js` 提交时除以 100：`Number(el('btTp').value || 0) / 100`；
- `service_backtest.py` 增加参数校验：`take_profit_pct` / `stop_loss_pct` 必须落在 `[0, 1)`，越界直接 400 并提示"应为小数（0.08 表示 8%）"，防止 API 调用方继续按百分数传。

### 2.3 验证

界面填 8 / 5 提交，后端收到 0.08 / 0.05，结果 `take_profit_exits = 206`、`stop_loss_exits = 216`。与命令行同参数跑出的指标逐位一致（11.89% / 2.027 / 1139 笔），说明换算正确且两条入口口径统一。

## 3. 缺陷二：自动 tag 撞号，覆盖历史结果目录

### 3.1 事故经过

`service_backtest.py` 原用进程内自增序号生成 tag：

```python
tag = "api_%d_%d" % (user_id, _next_seq())
```

服务重启后 `_seq` 归零，第一个任务又拿到 `api_2_1`——正是策略 3 的结果目录。该次界面提交覆盖了 `backtest/result_v2/api_2_1/` 下的 `summary.json` / `nav.csv` / `trades.csv`，而 `strategies` 表里策略 3 的指标仍是旧值，两边第一次出现不一致。

### 3.2 修复

改为时间戳命名，冲突时才加后缀：

```python
base = "api_%d_%s" % (user_id, time.strftime("%Y%m%d%H%M%S"))
```

并在函数注释里写明"这是本次实际发生过的数据损坏，不是假设"。

### 3.3 数据恢复

按原配置重跑写回同一目录：

```
--views fusion --prompt_version fusion-v1 --method weighted --score_th 0.0 --tag api_2_1
```

恢复后 `CumRet=16.88% ARR=53.30% SR=2.850 MDD=3.13% IR=-0.516 trades=523`，与策略 3 的 `metrics_json` 完全一致，自检 7 项通过。

### 3.4 修复后的行为

新任务 tag 为 `api_2_20261111031154` 这类时间戳，不再复用历史目录。

## 4. 缺陷三：接口写结果时漏写口径字段

`run_backtest_fusion.py` 会把 `views / method / score_th / prompt_version` 写进 `summary.json.config`，但 `service_backtest.py` 的 `_run()` 没写这四个字段。后果是界面提交的结果在报告页显示"单视角"——把"读融合表"说反了，属于不实陈述。

已补齐四行写入。修复后同一任务的口径行显示：

> 读融合表（fusion-vote-v1，weighted），50 只标的、5 日窗口、等权持有（仓位 95%）、佣金万三、印花税千一、滑点万五。止盈 8.0%、止损 5.0%（触发 206 / 216 次）。自检 7/7 项通过。准确率（逐股算完再平均）：0.5073。

## 5. 止盈止损实验：同一策略、只改止盈止损

策略 4（`api_2_20261111031154`）与策略 2（`api_f_v`）读同一张 `fusion-vote-v1`、同样 `score_th=0`，唯一差别是启用了止盈 8% / 止损 5%。

| 指标 | 策略 2（无） | 策略 4（止盈 8% / 止损 5%） | 变化 |
| --- | --- | --- | --- |
| 累计收益 | 21.07% | 11.89% | −9.18pp |
| 年化收益 | 68.82% | 36.04% | −32.78pp |
| 夏普 | 2.297 | 2.027 | −0.270 |
| 最大回撤 | 6.60% | 5.22% | −1.38pp |
| 信息比率（vs 等权） | +0.576 | −1.281 | −1.857 |
| 成交笔数 | 384 | 1139 | +755 |
| 止盈 / 止损触发 | 0 / 0 | 206 / 216 | — |

**可以写进论文的结论**：在该策略与该参数下，止盈止损降低了最大回撤 1.38pp，但同时把累计收益削掉 9.18pp，成交笔数增至近三倍（费用与摩擦同步上升），综合表现没有改善。

**不能写**：止盈止损提升了策略表现；止盈止损是有效的风险控制手段（本实验不支持这一结论）。它证明的是"参数可配置且真实生效"，不是"参数选得好"。

## 8. 答辩预案（本轮新增）

1. **"投票和加权到底在哪做的？"**
   在融合表生成阶段。`fusion-vote-v1` 是投票版，`fusion-v1` / `fusion-val-v1` 是加权版；回测只负责读表，`method` 对 fusion 路径不参与计算。

2. **"那我界面上的投票/加权下拉有什么用？"**
   对 `fusion` 视角不起作用（读表已固化），对多视角直连才起作用。这是当前实现的边界，已在口径卡片注明。

3. **"怎么证明止盈止损真的生效？"**
   策略 4 的 `take_profit_exits=206`、`stop_loss_exits=216`；三条早期策略为 0 是因为没启用，不是没实现。

4. **"为什么加了止盈止损反而收益更低？"**
   止盈提前卖出错过后续上涨，止损在震荡中反复被扫出，笔数从 384 增至 1139，费用从零增至 9.2 万。这是参数选择的结果，不是功能缺陷。

5. **"界面填 8 是 8% 还是 800%？"**
   8%。本轮修的就是这个换算，后端另有 `[0,1)` 校验兜底。

6. **"自动生成的结果目录会不会互相覆盖？"**
   曾经会（进程内自增序号在重启后归零），本轮已改时间戳，并恢复了一次被覆盖的历史结果。

## 9. 本轮没做的事

- 没有把三视角智能体从 12 天扩到全 test 段（成本与可复现性权衡，见第七节）；
- 编排层仍未跑满 97 个交易日（只有 2024-12-31 单日 50 只 + 12-16~12-31 另 600 条），按用户要求不消耗 token；
- 没有对三条早期策略回溯补配止盈止损参数（避免改动论文主线数字）；
- 社区跟投仍只有"帖子挂策略 + 一键订阅"，没有按作者跟投排行与取消订阅接口。
