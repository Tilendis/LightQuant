## R1 —— 原缺口：有「研判」没有「调度」　【已补，2026-11-14】

**课题原话**：「**调度**多个大模型（或不同分析视角的智能体）分别从技术面、基本面和情绪面**生成研判报告**，并通过投票或加权机制输出综合预测」

### 现状

| 环节 | 现状 |
| --- | --- |
| 三视角结果 | `judgements` 表 62,783 行，`view` 分 tech / fund / sent，每个视角一个 `prompt_version` |
| 怎么产生的 | `scripts/` 下的离线脚本批量跑完写库 |
| 系统运行时 | 只读表：`GET /api/judgements/{symbol}`（`api.py:318`）、`GET /api/judgements`（`api.py:414`） |
| 有没有"跑一次"的接口 | 补之前**没有**（34 个路由装饰器逐个查过）。现在有 `POST /api/judgements/run`，紧随 `GET /api/judgements` 之后 |
| 编排层的痕迹 | `fusion-agent-v1`（600 条），但也是离线生成的 |

### 缺在哪

课题这句话有两个动词：**调度**、**生成研判报告**。系统里两个都只有名词——有"研判表"，没有"调度动作"。评委如果追问「你的调度器是哪个模块」，只能指到一张表；追问「现场换一只票跑一次」，做不到。

对软件工程专业的课题，这一条是"系统"与"离线脚本＋查询界面"的分界线，值得补。

### 已补：怎么做的（实测于 2026-11-14）

新增 `app/service_judge.py` + `POST /api/judgements/run` + `DELETE /api/judgements/run/{pv}`，入参 `{symbol, date, allow_llm, write}`，一次调度三条链路并当场返回三份报告 + 融合结果。算法不另造，三条链路的判定逻辑与脚本逐行一致：

| 视角 | 调度内容 | 实现来源 | 实测耗时 |
| --- | --- | --- | --- |
| 技术面 | 本地 BiLSTM 十维特征推理，`score = 2p-1` | 与 `scripts/gen_tech.py` 同权重、同特征列、同窗口 | 22 ms |
| 基本面 | PE/PB 历史分位（0.6/0.4）→ 估值分 | 与 `scripts/gen_fundamental.py` 同一套规则 | 2 ms |
| 情绪面 | 当日新闻 → 智谱 LLM 打分；无 key 降级情绪词典 | 与 `scripts/gen_sentiment.py` 同一 prompt 契约 | 2 ms（规则降级） |
| 融合 | 0.90 / 0.00 / 0.10 加权，fund 与 sent 先去当日截面均值 | 与 `scripts/fuse_views.py` 同一公式 | 毫秒 |

**关键设计约束都守住了**：

- 写独立 `prompt_version`（`rerun-<时间戳>`），**不覆盖主口径 `fusion-test-3view`**；`DELETE` 只允许删 `rerun-*`，误删主口径会被拒。实测跑完 4 行、清理后全库回到 62,783 行。
- 无新闻时情绪面**弃权不落库**，不落 HOLD——落 HOLD 在投票里就是一张反对票（与 `scripts/gen_agents.py` 的既有语义一致）。
- 无 `ZHIPU_KEY` 时走情绪词典并标 `model='sent-lexicon-v1'`、`source='offline_rule'`，不冒充大模型研判。
- 权限：`need(user, "author", "operator")`，实测投资者身份调用返回 403。

**耗时**：模型冷启动（含 `import torch`）49.4 秒；接入 `_warm_engine` 后台预热后，单次调度 73–95 ms，用户点一下即出结果。

前端：研判页 K 线下方加「研判日期 + 重新研判」工具条，结果单独一块表格（逐视角信号/理由/来源/耗时 + 融合 + 去均值说明 + 弃权提示），与下面的主口径主表并存，互不影响。

### 判断

- **可行性：高，已完成**。三个视角的生成逻辑本来就在 `scripts/` 里，工作量确实是"搬函数 + 一个路由 + 一个按钮"，未新增算法。
- **价值：最高**。这是课题原文两个动词（调度、生成研判报告）的唯一落点，答辩时可以现场换一只票跑一次，而不是只能翻历史结果。
- **遗留风险**：① 技术面的标准化仍用该股全序列均值方差（继承自原仓库），这是已知前视泄漏，返回里已标注、未修正；② 情绪面覆盖稀疏，12 月仅个别交易日有新闻，演示要挑有新闻的日子（万华化学最后一条新闻是 2024-12-02），否则该视角弃权；③ 单标的调度没有真正的横截面，去均值改用"当日库里已有分数"的均值，当日不足 5 只时退化为不去均值并在返回里标明。

## R2 —— 已补：页面上能选「预测来源」了（实测于 2026-11-14）

**课题原话**：「策略作者**基于预测结果**配置止盈止损参数并提交异步回测任务」

### 补之前是什么样

后端本来就是完整的：`DEFAULT_PARAMS` 的 `views` 默认 `["fusion"]`，`normalize_params` 校验 tech / fund / sent / fusion 四类，`fusion_version` 按回测起点派生，注释明写「传 tech/fund/sent 可以跑单视角消融」。

**但前端写死了**：`body.views = ['fusion']`。回测页只暴露了 `btMethod` 一个下拉（加权 / 投票）。

### 缺在哪

课题要求「基于预测结果配置」，而页面上能配的只有止盈止损和成本——**「用哪个预测结果」这件事在界面上根本不存在**。评委看到的永远是「读融合表」，看不到三视角可以单独跑。

### 改成什么样了

回测页工具条现在是：`策略类型 | 预测来源 | 融合方式 | 起始 | 结束 | 止盈% | 止损%`。

| 预测来源 | 请求体 | 说明 |
| --- | --- | --- |
| 融合结论（三视角合成） | `views=['fusion']` + `method` | 选它时才出现「融合方式」下拉（加权 / 投票） |
| 仅技术面 | `views=['tech']` | 不传 `method`，`fusion_version=None` |
| 仅基本面 | `views=['fund']` | 同上 |
| 仅情绪面 | `views=['sent']` | 同上 |
| 基本面 + 情绪面 | `views=['fund','sent']`、`weights=[1,1]` | 两视角等权加权和，不读融合表 |

另外两处防误读：切成「截面选股」时 `#btViews` 一并禁用（截面路径固定只读技术面分数）；选单视角 / 多视角时提示文案分开写，不共用一句。

### 实测记录

同一界面、只换预测来源，各 2.2 秒跑完：

| 预测来源 | 止盈/止损 | 累计收益 | 年化 | 夏普 | 成交笔数 | 信息比率 |
| --- | --- | --- | --- | --- | --- | --- |
| 融合结论 · 加权 | 0 / 0 | 15.9714% | 50.06% | 3.5666 | 1003 | −0.4964 |
| 仅技术面 | 8% / 5% | 9.7976% | 29.18% | 3.0079 | 1138 | −1.1143 |

第一行与主口径 `fusion-test-3view`（`cum 0.159714041490 / arr 0.500602104469 / sharpe 3.566599483684 / trades 1003`）**逐位一致**，说明「融合结论·加权」这条路跑的就是主口径，不是另起一套算法。

参数层同时验过 9 种组合：5 档合法 source 全过；「融合 + 技术面混用」「未知视角 `orch`」「止盈传 8」三种被拒。

测完删掉两个任务行与产物目录，`backtest_tasks` 回到 20 行。

### 必须说清的边界

- 单视角那行（9.79%）**只是「换预测源能跑通」的证据，不是主结果**，也不能和主口径横比：它的止盈止损是 8%/5%，主口径是 0/0。
- 界面能选单视角，**不等于**单视角被验证为有效。它证明的是「三视角可以分别关闭、能各自跑」——这是消融能力的证据，不是效果的证据。
- 截图：`docs/screenshots/27-策略回测-预测来源可选.png`。

## R3 —— 已补：推进日期不再硬编码，账户有了自己的交易日（实测于 2026-11-14）

**课题原话**：「投资者可订阅策略进行模拟跟单」

### 补之前是什么样

`POST /api/follow-accounts/{aid}/advance` 接收可选 `date`，不传时 `advance_account` 自动推到曲线末端——接口本身没错。问题在前端两处：

1. `app/static/app.js` 把日期**写死**成 `body: { date: '2024-12-31' }`。数据集到 12-31 结束，所以看不出错，但换一份数据就会静默推到错的日期；更要紧的是，代码里出现写死的日期，读起来像「净值是离线算好摆上来的」。
2. 推进是**手动**的，而且只能推「刚订阅的那个账户」——别的账户在表里没有按钮。

### 改成什么样了

| 环节 | 落点 | 说明 |
| --- | --- | --- |
| 账户交易日 | `follow_accounts.as_of`（`schema.sql`，`db.py:_migrate` 幂等 ALTER） | NULL = 订阅后还没推过。老库 `current_nav <> initial_nav` 的账户回填为 `MAX(prices.date)` |
| 交易日历 | `service_risk.trade_days()` / `next_trade_day()` + `GET /api/trading-days` | 195 个交易日（2024-03-15 ~ 12-31）。取 `prices` 的 `DISTINCT date`，不是某只票的 K 线——单票停牌日仍是交易日 |
| 推进一日 | `service_risk.step_account()`，`POST /api/follow-accounts/{aid}/advance` body 留空 | 按该账户 `as_of` 取下一交易日；`as_of` 为空时落在**该策略净值曲线首日**（策略 7 是 2024-08-14，不是全库首日 03-15，否则会撞「早于策略净值起点」） |
| 批量推进 | `service_risk.advance_all()` + `POST /api/follow-accounts/advance-all` | 每个在途账户**各自**走一天。不统一 target：老账户已到期末、新账户还没开始，统一取最新会拉平落后账户，统一取最落后会让已到期末的账户净值倒退 |
| 推到期末 | body `{"date": "latest"}` | 显式要求才这么做，默认不再是这个行为 |
| 前端 | 订阅表加「净值截至」列；ACTIVE 行加「推进一日」；工具条加「推进全部账户」与「系统当前交易日」一行 | 页面上**不再出现任何写死日期** |

### 实测记录

1. 新订阅策略 7 → `as_of` 为空、净值 100,000。
2. 连点「推进一日」3 次：`2024-08-14` / `08-15` / `08-16`，净值 100,000 → 100,761 → 100,995.82，峰值同步跟涨。
3. 点「推进全部账户」→「推进一天：1 个账户前进，5 个已到期末（最新 2024-08-19）」。
4. `GET /api/trading-days` → `count=195 first=2024-03-15 last=2024-12-31`。
5. 同一日期重复推两次，`as_of / current_nav / peak_nav` 完全一致（幂等）。
6. `2024-09-14`（周六）→ 400「不是交易日」，不再被 cutoff 静默吞成周五。
7. `author` 调 `advance-all` → 403。
8. 测完删除新建的订阅与账户，库回到 5 个账户 / 5 条订阅 / 6 条风控事件 / 62,783 行 `judgements`。
9. selftest 从 71 项扩到 **76 项**，连跑两遍 76/76 过。

### 这次没有做、需要提前说明的

- **没有做定时任务**。"自动跟随"仍然是「点一次走一天」或「进页面按需推」，没有挂 cron 每天自动推。理由是：这套系统的行情是固定 195 个交易日的离线切片，挂真实定时器只会把演示数据一路推到底，反而看不出逐日变化。答辩时讲成「推进由系统按交易日历驱动，可单步、可批量」，不要讲成「实时自动跟单」。
- **`as_of` 的老数据回填策略**：按「`current_nav <> initial_nav` 即回填为行情末端」处理。如果以后按各策略 `nav.csv` 末端分别回填，这条需要改。
- 截图：`docs/screenshots/26-策略与订阅-推进一日.png`。

## R4 —— 已补：强平监控不再靠点「扫描」（实测于 2026-11-14）

**课题原话**：「风控员负责**监控**模拟盘强平预警与社区发帖违规拦截」

### 补之前是什么样

- 账户水位表是只读的（`loadRisk()` 注释写明「只读，不推进」），「距强平线」只是表格里一列数字
- 预警事件 `MARGIN_CALL` 要靠点「扫描」（`POST /api/risk/scan`）才产生
- 库里有 2 条 `MARGIN_CALL`，说明链路是通的

### 缺在哪

「监控」做成了「巡查」——不点就没有新事件；而「距强平线」一列数字，看不出整体危险度。

### 核完之后，缺口比原来记的小

原以为「预警要靠人点扫描才产生」。核代码发现：**强平判定本来就挂在账户推进里**——`advance_account()` 逐日遍历时就在算 `stop_nav` / `liquidate_nav`，`if event:` 直接写 `risk_events`，同 `(account, kind, date)` 已有去重。

所以真实缺口只剩两条：① 页面打开时没有任何汇总，得自己一列一列看；② 「扫描」与「推进」的分工在界面上没讲清，容易被理解成「只有点了扫描才在监控」。

### 改成什么样了

1. 风控页表格上方加一条汇总（`#riskSum`）：

   > 在途 5 个账户；距强平线最近的是 #5，+1.54%；其中 2 个不足 3%（按曲线末端水位只读计算）。强平判定随账户推进自动执行并写风控事件，不必点「扫描」。

2. 颜色按最危险那个账户分档：不足 1% 红、不足 3% 黄、其余灰。
3. 汇总数据来自 `GET /api/risk/accounts`（`inspect_all`，`dry_run=True`）——进页面算一遍，**看一眼不会改库，不会因为「看了一眼」就把账户标成已预警**。

### 实测记录

订阅策略 7、强平线 3%、本金 10 万，然后**只做一件事：推到期末**，全程不调 `/api/risk/scan`：

- `risk_events` 6 → 7，新增 `#9 MARGIN_CALL account=11 date=2024-09-09 nav=98759.66 stop=99047.41 peak=102110.73 回撤=-3.28%（强平线 3%）`
- 推进返回 `event=MARGIN_CALL / warn_date=2024-09-09 / max_dd_pct=-3.63`

结论：**推进一次就自动判定并落事件，不需要手点扫描**。测完删掉账户与订阅，`risk_events` 回到 6。

页面实测（风控员身份）：汇总条文案如上；账户表 9 列；风控事件表 6 条未新增；控制台无错。截图 `docs/screenshots/28-风控页-强平监控汇总.png`。

selftest 76 → **77** 项（新增「水位字段够算页面汇总」，卡的是 `liquidate_nav` / `max_dd_pct` / `event` / `as_of` 四个字段是否都在）。

### 必须说清的边界

- 这是**演示级的「监控」**：进页面按只读水位算一遍、推进时自动判定。**没有后台常驻任务，也没有行情轮询**——离线数据的库里不需要。要达到「没人打开网页也每天自动扫」，得挂定时任务，本项目没做。
- 汇总里的水位是 `dry_run` 按曲线末端（或复盘日期）算的，**不是账户真实 `as_of`**，所以文案只写口径不写日期，免得和订阅页「净值截至」对不上。
- 去重按 `(account_id, kind, date)`，date 取本次重算的 `first_call`。**峰值抬升会让早期回撤点变浅、`first_call` 后移，同一账户可能在新日期再出一条**——这条是「历史上又一次触及强平线」的真实记录，不是重复写；同一 `peak` 下反复扫同一天不会重复。
