## 一、本轮自查查出两个真缺陷（不属于"借鉴"，属于必修）

### 缺陷 1：主口径 `fusion-test-3view` 的 tech 输入混了版本

**这是可复现的确定缺陷，不是推测。**

`scripts/fuse_views.py:33` 的 `load_matrix(conn, view, start, end, prompt_versions)` 声明了 `prompt_versions` 参数，但 `36` 行的 SQL **没有用它**：

```sql
SELECT symbol, date, score, signal FROM judgements
WHERE view = ? AND date BETWEEN ? AND ?
```

然后 `41` 行用 `pivot_table(..., aggfunc="last")` 聚合。同一 `(symbol, date)` 在 `tech` 视角下存在多个 `prompt_version` 时，取行序最后一条——**也就是 rowid 最大的那条**。

库里的 rowid 时序（同一张表，rowid 单调，可据此判定写入先后）：

| 版本 | rowid 区间 | 条数 | test 段覆盖 |
| --- | --- | --- | --- |
| `tech-v1`（BiLSTM） | 224 ~ 62210 | 9100 | 2024-08-14 ~ 12-31，93 天 |
| `tech-llm-v1`（LLM 写理由） | 44911 ~ 48310 | 1100 | 2024-12-02 ~ 12-31，22 天 |
| `tech-llm-blind-v1` | 44961 ~ 46060 | 1100 | 2024-12-02 ~ 12-31，22 天 |
| `tech-agent-v1` | 48315 ~ 51060 | 600 | 2024-12-16 ~ 12-31，12 天 |
| **`fusion-test-3view`** | **73061 ~ 77806** | 4746 | 08-08 ~ 12-31 |

`fusion-test-3view` 的 `min(rowid) = 73061`，大于 `tech-llm-v1` 的 `max(rowid) = 48310`——**生成融合时库里已经有 LLM 版了**。

按「同 `(date, symbol)` 取 rowid 最大者」实际生效的 tech 版本分布：

| 最终生效版本 | 条数 | 覆盖区间 |
| --- | --- | --- |
| `tech-agent-v1` | 600 | 2024-12-16 ~ 12-31 |
| `tech-llm-v1` | 500 | 2024-12-02 ~ 12-15 |
| `tech-v1`（BiLSTM） | 3550 | 2024-08-14 ~ 11-29 |

即 **12-02 之后的 1100 个格（占 4746 的 23.2%）用的不是 BiLSTM 分数，而是 LLM 版 / agent 版分数**。

**只读复现结果**（不动库，用同样逻辑重算）：

| 口径 | BUY | SELL | HOLD | 12 月 BUY |
| --- | --- | --- | --- | --- |
| A：只用纯 `tech-v1` | 317 | 364 | 4065 | **68** |
| B：混版本（= 库里现状） | **320** | **335** | **4091** | **3** |
| 库里 `fusion-test-3view` 实际 | 320 | 335 | 4091 | 3 |

B 与库里实际**逐位一致**，说明聚合行为就是行序最后一条。A 与 B 有 1100 个格分数不同。

**后果有三层**：
1. 所有文档里「`0.90 × tech(BiLSTM) + 0.10 × sent`」的表述在 12 月不成立。
2. **「12 月只剩 3 条 BUY、策略 10–12 月基本空仓」不是策略保守，是输入被换成了 LLM 版。** 纯 BiLSTM 口径下 12 月应有 68 条 BUY。
3. 回测 15.97% / SR 3.567 这个数混合了两种 tech 打分器，口径描述与实际不符。

**修复成本**：`fuse_views.py` 一处（把 `prompt_versions` 真正接进 SQL），然后重跑 `fusion-test-3view` + 主口径回测。CPU 环境约半小时。

**修复风险**：15.97% 会变（可能变好也可能变差），README、三份 docs、策略 #7 的 `metrics_json` 都要同步。这件事动的是主口径，需要你先点头。

### 缺陷 2：同一问题也污染了 `fusion-val-3view`

`fusion-val-3view` 的 rowid 是 63485 ~ 68160，同样在 `tech-llm-v1`（44911~48310）之后，同理会取到 LLM 版。验证集标定的证据链（`docs/calib_weights_3view.json`）如果是从这张表算的，也受影响。

不过 `calibrate_weights.py` 是自己重算 tech 分数的（`tech_scores()` 直接跑 BiLSTM 推理），不读 `judgements` 表，所以**权重标定本身是干净的**。受影响的是 `fusion-val-3view` 这张落库表。

## 二、值得借鉴的前人经验

按「可行性 × 价值」排序，每条给出处、人家怎么做、我们现状、落地方式。

### P0：低成本、对答辩直接有用

#### P0-1 情绪面外推加时间衰减

**出处**
- FNSPID（`arxiv 2402.06698`）：新闻缺失日用指数衰减补齐，`S(t) = S(0)·e^(−λt)`，取 `λ = 0.03`
- `arxiv 2603.23568`：同一时间桶内的新闻按 recency 加权，`W_time = exp(−γ(t_end − t_i))`
- QuantArmy 的 LLM 信号回测模块：半衰期 `h = 2` 天，即昨天的新闻权重 71%、前天 50%

**我们现状**：`fuse_views.py:130-137` 是纯 `ffill`，代码注释自己写了「局限：简单 ffill 假设新闻影响持续到下一次新闻，未做衰减，论文里要写明」。`calibrate_weights.py:139` 同样。

**后果**：sent 在 test 段只覆盖 920 / 4850 格（18.97%），其余靠 ffill；2024-12 全月只有 128 个标的日有新闻。一段 10 月的新闻可能一直影响到 12 月，且权重不减。这也是情绪面 0.5054 这个数字不干净的原因之一。

**落地**：在 `fuse_views` 与 `calibrate_weights` 两处把 `ffill()` 换成「按 gap 天数衰减的 ffill」，半衰期做参数（建议先跑 h=2 与 h=5 两档）。重跑标定看 sent 权重是否还保得住 0.10。

**可行性**：高（两处改动，纯 pandas）。**价值**：高（这是审稿人一眼能看出的方法缺陷，补上就从"知道有局限"变成"处理了局限"）。**风险**：会动主口径，需重标权重；sent 权重可能进一步下降。

---

#### P0-2 给四个视角补标准化的因子检验口径（IC / RankIC / ICIR / 分层）

**出处**
- 华泰《因子合成方法实证分析》（多因子系列之十）：IC 法、回归法是单因子测试的两种标准做法，合成用等权 / 历史 IC 加权 / 最大化 IC_IR 加权等 6 种
- 山西证券《多因子报告之一：因子测试框架和估值因子初测》：给出 IC 均值、IC 标准差、IR、IC>0 占比的完整报表格式
- FactorHub：`|IC| > 0.03` 通常视为有统计显著性，稳定在 0.05 以上属高质量因子
- CSDN《因子研究的 8 个步骤》：数据准备 → 因子构造 → 预处理 → 中性化 → 单因子检验（IC）→ 分层回测 → 多因子合成 → 样本外验证与衰减

**我们现状**：只有 `view_accuracy.json` 里的一个 ACC 数字 + 一句「fund 的 IC 是 −0.0112」（散落在文档里）。没有逐日 IC 序列、没有 RankIC、没有分层净值、没有衰减曲线。

**为什么这条价值高**：现在说「fund 0.4940 是因为 IC 接近 0」，是一个孤立数字；换成「逐日 IC 序列均值 −0.0112、ICIR −0.0X、IC>0 占比 4X%、五档分层净值无单调性」，是因子研究的标准语言。后者能同时解释三件事：fund 为什么权重 0、sent 为什么覆盖率低就无效、tech 为什么 ACC 0.5482 但强信号 0.6447。

**落地**：新写一个 `scripts/eval_factor.py`，读 `judgements` + `prices`，对每个 `prompt_version` 输出 IC 序列、ICIR、t 值、五档分层累计收益、IC 衰减（滞后 1/2/3/5 日）。纯只读计算。

**可行性**：高（半天）。**价值**：高。**风险**：算出来 fund 的 IC 依然接近 0——但这是事实，有完整 IC 报表反而更可信，而且能正面回答"你凭什么给基本面 0 权重"。

---

#### P0-3 多重检验校正（DSR / PBO）

**出处**
- Bailey & López de Prado, *The Deflated Sharpe Ratio*（`davidhbailey.com/dhbpapers/deflated-sharpe.pdf`）：DSR 同时校正「试验次数 N」与「非正态（偏度/峰度）」
- `bhavishy.dev/blog/alphaaudit.pdf` 的复现审计：结论是「DSR 而非样本外检验才是真正的约束条件——校正搜索次数剔除的『显著』异象，比单纯用时间外样本剔除的更多」
- PyPI `deflated-sharpe`：纯 Python 零依赖实现
- 配套的 PBO（Probability of Backtest Overfitting）

**我们现状**：库里 6 条策略、两组 0.05 步长的权重网格（各 21 档）、多组截面对比（TOP10/五日轮动/剔除段）——**搜索次数不少，但报告里只报原始 Sharpe 3.57 / 3.676**。

**落地**：对主口径与截面策略各算一次 DSR，`N` 用实际搜索过的组合数（权重网格 21 × 2 + 策略变体 ≈ 50 量级），`T` 用日收益样本长度，偏度峰度由收益序列算。同时给截面策略算 PBO。

**可行性**：高（纯计算，公式公开，半天内）。**价值**：高——「我做了多重检验」是硬证据，比「我们注意了过拟合」有力得多。**风险**：**算出来大概率不显著**。主口径 SR 3.57 是在 93 天样本上、且 IR 为负（−0.4964），`T` 短、搜索多，DSR 很可能掉到 0.5 以下。要有心理准备：这条做出来的结论可能是「原始 Sharpe 不可信」，而这恰恰是诚实的结果。

#### P0-4 基准口径统一 + IR 定义写清

**出处**：IR 的标准定义 `IR = (Rp − Rb) / 跟踪误差`，即超额收益除以超额收益的标准差（J.P. Morgan、State Street、Quantopia 的口径一致）。

**我们现状**：主口径基准是「50 只等权买入持有」从 **08-14** 起（`engine_v2.py:349/368`），截面引擎基准同样等权但起点 **08-08**（`engine_cross_section.py:171-174`）。两个基准收益因此不同：主口径 19.04%、截面 14.63%。这是已知未决问题。

**后果**：现在 README 里「跑输基准 3.07pp」用的是 19.04%，而截面策略的「+53.80% vs 基准 +14.63%」用的是另一个基准。两个数字放在同一份材料里会被追问。

**落地**：把两个引擎的基准起点与成分口径对齐（都用区间内可交易的全部标的等权、都从第一个有信号的日期起算），或至少在报告里显式标注「两个基准不可横比」。

**可行性**：高。**价值**：中高（避免被问倒）。**风险**：对齐后截面策略的超额会变（14.63% → 可能接近 19%），+53.80% 的优势会被压缩。

---

#### P0-5 涨跌停可成交性从「近似」升级为「三态判定」

**出处**
- 《A股量化策略体检手册》：一字板成交概率≈0，直接剔除；T 字板按封单量/成交额估概率；换手板可成交但需加滑点；跌停卖出概率≈0，需延迟到次日
- 腾讯云开发者社区《回测里的涨停判断，为什么不能写成 return >= 0.1》：价格到达涨停不等于全天无法成交，日线只能看到 OHLCV，无法还原盘口深度；建议分「未触及涨停 / 触及但盘中打开 / 全天一字涨停」三态
- 迪雅数据：涨停价必须按「昨收 × (1+涨跌幅限制)」四舍五入到分计算，四舍五入规则直接决定打板回测成败

**我们现状**：`engine_v2.py:143` 只有 `one_word_board = high == low` 一条近似，`164/194` 跳过买入或卖出。代码 `15-17` 行注释自己写了「不等于实现涨跌停规则」。

**落地**：按昨收算涨停价（区分主板 10% / 创业板科创板 20% / ST 5%），判断 `high >= 涨停价` 且 `low >= 涨停价`（一字板）→ 不可买；`low <= 跌停价` 且 `high <= 跌停价`（一字跌停）→ 不可卖且顺延次日。

**可行性**：中（要拿到每只票的板块属性——`stocks` 表有 `code`，可用前缀判断；ST 状态我们没有数据）。**价值**：中（我们 50 只都是大票，一字板极少，实际影响应该很小；但对论文「执行假设」章节是实打实的加分）。**风险**：可能微调回测结果。

### P1：中等成本，需先掂量

#### P1-1 LLM 结果的时间污染量化（不是只写一句"有风险"）

**出处**
- `arxiv 2512.23847` *Detecting Lookahead Bias in LLM Forecasts*：构造 LAP（Look-Ahead Probability）指标，正样本期内显著为正、训练截止后立刻塌到 0；用「LAP × LLM 预测」的交互项在回归里显著，作为污染的证据
- `arxiv 2510.07920` *Profit Mirage*：用「历史交易期 vs 最近交易期」两段对照，市场收益相近但 LLM 表现差异巨大
- `vbase.com/blog/llm-alpha-look-ahead-bias`：DeepSeek 3.2 从 +20.73% 年化 alpha 掉到 −1.04%
- `aclanthology 2026.emnlp-main.510`：把这种现象命名为 parametric look-ahead bias，并指出「未校正的长窗口回测系统性误导，而唯一无偏的短窗口又太短、撑不起统计结论」

**我们现状**：`view_accuracy.json` 的 `meta.note` 只写了一句「测试期在训练语料覆盖区间内，存在语料污染风险；该指标用于横向比较各视角，不作为有效性证据」。没有量化。

**能做的量化（不需要新数据）**：我们手里天然有一组对照——`tech-v1`（本地 BiLSTM，**训练数据截止 2024-03-14，绝对干净**）与 `tech-llm-v1`（同一方向、LLM 写理由）。两者方向一致性、以及 LLM 版在「LLM 可能见过」的 12 月区间相对 BiLSTM 的偏移量，可以作为一个间接的污染度量。

**落地**：算两组——(a) `tech-llm-v1` 与 `tech-v1` 的信号一致率、分数相关；(b) 把 `tech-llm-blind-v1`（盲测版，看不到涨跌结果）与 `tech-llm-v1` 对比，看「知道结果」是否让 LLM 更准。如果 blind 版显著更差，就是污染的直接证据。

**可行性**：中高（纯只读计算，两组版本都已落库）。**价值**：**高**——这是答辩必被追问的点，能量化比"承认有风险"强得多，而且我们已经有现成的对照组，不需要新数据。

#### P1-2 稳健性从「剔段」扩到「按行情状态分段」

**出处**：`bhavishy.dev/blog/alphaaudit.pdf` 的核心结论之一是「要求跨宏观状态稳健，是比任何单一显著性检验都强得多的过滤器」。

**我们现状**：截面引擎已有 `cum_drop_best_1/2/3`（`engine_cross_section.py:179-219`），剔除最好 1/2/3 段后重算累计。这是好的起点。

**但现有的问题**：`cs_test_api2` 剔 1 段后只剩 **16.54%**，仅比基准 14.63% 高 1.91pp；剔 2 段 8.76%、剔 3 段 4.97%。也就是说 **+53.80% 这个数字高度依赖少数几段**。这个结论目前只在 `KEY_FACTS` 里，没有正式写进任何交付文档。

**落地**：补三种切分——按自然月、按「基准上涨/下跌/震荡」三态、按调仓序号的四分位，各算分段收益与胜率。同时把「剔段后仅剩 16.54%」这条**写进 README 和对照文档**，不要等评审自己算。

**可行性**：高（纯计算）。**价值**：高（主动披露比被动挨问强）。**风险**：无。

#### P1-3 覆盖偏差（MNAR）的显式处理

**出处**
- `jordimondria.com/assets/papers/WiseCrowds.pdf`：最小市值股票中，分析师推荐缺失 98%、新闻缺失 81%，而 StockTwits 只缺 13%——覆盖缺失不是随机的，与市值强相关
- `arxiv 2604.26811`：投资者对新闻的反应非线性衰减，缺失值应按指数衰减插补

**我们现状**：news 覆盖 2320 / 9750 = 23.79%（全库），test 段 18.97%。50 只标的全是同一批（CSMD50），**没有市值分层信息**，所以无法证明"缺失与市值无关"。当前用 ffill 补齐，等价于假设「没新闻 = 新闻没变」，这是典型的 MNAR 误处理。

**落地**：两种做法二选一——(a) 给 `sent` 加一个「距上次新闻的天数」作为显式特征，让下游知道这个分是外推了几天的；(b) 只在覆盖充足的子样本上评估 sent，其余标为「不可用」而不是 ffill。方案 (a) 更符合工程直觉，也能直接进前端展示。

**可行性**：中（要改 `fuse_views` 与落库结构，加一列 `stale_days`）。**价值**：中高（这条是方法论层面的，能进论文的「局限性」章节并且是「已处理」而非「已承认」）。**风险**：要改 schema。

### P2：成本明显偏高，先不做

#### P2-1 Purged K-Fold / Walk-Forward 交叉验证

**出处**：López de Prado《Advances in Financial ML》第 7 章；PyPI `purgedcv`（scikit-learn 兼容，含 `WalkForwardSplit` 与 CPCV）；open-quant 的 `PurgedKFold`；标准做法是 purge（剔除标签与测试集重叠的训练样本）+ embargo（测试集之后加 5–10 天缓冲，日频常用 1% 数据长度）。

**我们现状**：单次三段切分（train ≤ 03-14 / val ≤ 08-07 / test ≥ 08-08），来自 `utils/util.py`。标签是 `Close(t+1) > Close(t)`，**重叠仅 1 天**，purge 的必要性远低于多日标签场景。真正的问题不是泄漏，是**只有一次切分、一个 test 段**。

**为什么不急**：改成 walk-forward 意味着 BiLSTM 要重训 N 次。CPU 环境（torch 2.4.1+cpu）上单次训练已经是小时级，滚动 5 折大约要按天算。

**结论**：**不做**。在论文里说明「标签为 1 日方向、重叠 1 天，purge 收益有限；单次切分是本研究的已知局限」，比硬上 walk-forward 更诚实也更省时间。

#### P2-2 辩论式多智能体（Bull / Bear debate）

**出处有矛盾，这点很重要**：
- TradingAgents（`arxiv 2412.20138`）用 Bull/Bear researcher 多轮辩论 + 风险团队，报告称优于基线
- 但 `arxiv 2508.17536` *Debate or Vote* 的结论是：**多数投票贡献了 MAD 的绝大部分增益，多数情况下无辩论的多数投票与完整辩论持平**
- `arxiv 2605.30802` 更直接：加权投票 83.43% > 最好的单模型 82.42%，而**审议式共识反而降到约 76%，低于所有单模型基线**，归因于「说服性错误传播」与 LLM 的阿谀倾向
- `arxiv 2512.02405` WISE 的加权迭代又能提 2–7%

**我们现状**：已有 `fusion-vote-v1`（多数投票）与 `fusion-agent-v1`（编排层 weighted-agent）。两条路子都已经在库里。

**结论**：**不做辩论**。文献本身互相矛盾，且我们没有能证明增益的样本量（600 条 / 12 天），DeepSeek 余额只剩约 1.30 元。再加一层辩论只会重复已有工作。

---

#### P2-3 分层记忆与反思（FinMem / FinAgent）

**出处**：FinMem（`arxiv 2311.13743`）的 working memory + 分层长期记忆（observation / summarization / reflection 三操作）；FinAgent（`arxiv 2402.18485`）的双层反思模块 + 多样化记忆检索。

**我们现状**：每次研判都是独立无状态的，同一标的昨天判了什么、结果如何，今天的 agent 不知道。

**为什么不急**：要改 `gen_agents.py` 的 prompt 构造并重跑，**烧 token**；而且 12 天窗口的统计功效不足以证明"有了记忆更好"。这条属于"如果以后扩到全 test 段再考虑"。

## 三、不建议做的

| 项 | 理由 |
| --- | --- |
| 辩论式多智能体 | 文献结论互相矛盾（`2508.17536` 说投票=辩论，`2605.30802` 说共识反而更差）；已有投票与编排两条路子 |
| 换 GPU 重训做 walk-forward | CPU 环境跑不动，且 1 日标签的 purge 收益本来就有限 |

| 用 2025 年数据重跑证明无污染 | 手上没有 2025 数据，抓取成本高；P1-1 的间接方法已经够用 |
