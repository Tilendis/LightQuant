# 融合主口径与情绪面覆盖口径

本文只写两件事：**哪个融合方式算主口径、哪个只算对照**，以及**情绪面到底覆盖了多少、没有新闻时怎么处理**。
文中每个数字都标了来源，可直接在库或 `summary.json` 里复算。凡标"待补"的，是本文没做完、不许当成已完成的。

---

## 1. 主口径定为加权（weighted），投票（vote）降为对照

### 1.1 为什么不是投票

投票在当前系统里**不是"略差"，而是没有统计效力**。

`docs/三分析师预实验诊断.md` 第 142、225 行记录的两次实测：

| 融合方式 | 有效样本（非 HOLD） | 准确率 |
| --- | --- | --- |
| vote | 2 | 0.5000 |
| vote（第二次） | 6 | 0.5000 |
| weighted | 260 | 0.4577 |

原因不是实现错了，是结构性的：**三视角大多数日子给 HOLD，多数决在 HOLD 占多数时必然失效**。
`judgements` 里 `fusion-vote-v1` 全段 4850 条中 HOLD 占 3559 条（73.4%），非 HOLD 仅 26.6%，
三个视角同时非 HOLD 的日子更少。所以投票这一路只能作对照，不能作主口径。

### 1.2 主口径的技术路径

```
三视角（tech / fund / sent）
  → 验证集标定权重（docs/calib_weights.json：w_tech=1.0, w_fund=0.0）
  → score 加权 Σw·score / Σw，|score|>0.05 才给方向
  → 落库 prompt_version = fusion-val-v1
  → 回测读这张表（method 在 fusion 路径上不参与计算）
```

权重为什么 fund = 0：验证集 2024-03-15~08-07 实测 `fund_only` 准确率 0.4792（低于 0.5，
且 mean_next_ret 为负），`tech_only` 0.5538，标定结果把基本面权重压到 0。
这是"权重可以设为 0"的设计被实际用上了，不是把基本面模块删掉——模块仍在、仍落库、仍在界面上出信号。

### 1.3 主口径基准（本轮新跑）

命令：

```
python backtest\run_backtest_fusion.py --views fusion --prompt_version fusion-val-v1 \
       --method weighted --score_th 0.0 --tag api_fusion_val_main
```

结果见 `backtest/result_v2/api_fusion_val_main/summary.json`：

| 指标 | 值 |
| --- | --- |
| 标的 / bar | 50 / 93（2024-08-14 ~ 12-31） |
| 累计收益 | 15.10% |
| 年化 | 46.98% |
| 夏普 | **3.373** |
| 最大回撤 | 3.34%（08-30 → 09-13） |
| Calmar | 14.09 |
| 成交笔数 / 费用 | 973 / 81,614.67 |
| 逐股平均准确率 | 0.5458 |
| 基准（等权买入持有） | 19.04%，回撤 9.74% |
| 信息比率 vs 等权 | **−0.617** |
| 自检 | 8/8 通过 |

### 1.4 三条结果的横比（同一 test 段，必须放在一起看）

| 策略 tag | 读的表 | method | 累计 | 夏普 | 回撤 | 笔数 |
| --- | --- | --- | --- | --- | --- | --- |
| `api_fusion_val_main`（**主口径**） | fusion-val-v1 | weighted | 15.10% | 3.373 | 3.34% | 973 |
| `api_2_1`（策略 3） | fusion-v1 | weighted | 16.88% | 2.850 | 3.13% | 523 |
| `api_f_v`（策略 2，对照） | fusion-vote-v1 | vote | 21.07% | 2.297 | 6.60% | 384 |

**可以说**：加权版在夏普（3.373 vs 2.297）和回撤（3.34% vs 6.60%）上优于投票版；投票版累计收益最高，
但它的回撤多一倍、且融合层有效样本只有个位数。

**必须同时说**：主口径的最优夏普策略**跑输等权买入持有 3.94pp**（15.10% vs 19.04%），IR −0.617。
本窗口等权基准涨了 19%，策略的仓位约束（95%）、逐股独立账户与频繁调仓把收益吃掉了一部分。
**不能**把"夏普最高"说成"策略更好"——它在这个窗口没有跑赢最简单的买入持有。

**不能**做的两件事：把 21.07% 当成主结果（那是投票版）；把三条策略的数字放在一张表里直接比大小
（读的表不同、权重口径不同，属于跨口径横比）。

### 1.5 已经在代码里固化的部分

| 位置 | 现状 |
| --- | --- |
| `app/service_backtest.py` `DEFAULT_PARAMS["method"]` | `"weighted"` |
| 同文件 `normalize_params` | `weighted → fusion-val-v1`，`vote → fusion-vote-v1` |
| `app/static/index.html` `#btMethod` | 第一项即"加权融合"，默认选中 |
| `app/api.py` `strategy_activity` 默认参数 | `prompt_version="fusion-val-v1"` |
| `scripts/orchestrate.py` 输出 json | 写明"本层不进入回测信号链，回测仍读 fusion-val-v1" |

**没做的**：策略 2、4 仍挂着 `method=vote`。它们是历史实验记录，本轮**不修改已发布策略的数字**
（改了就等于回填实验结论）。要改成加权版需重跑并重发策略，这是另一件事，见第 4 节。

## 2. 情绪面覆盖：21.57%，不是满覆盖

### 2.1 覆盖率实测

| 项 | 数值 | 来源 |
| --- | --- | --- |
| `prices` 行数（标的×日） | 4850（50 × 97） | `SELECT COUNT(*) FROM prices` |
| `news` 行数 | 3026 | `SELECT COUNT(*) FROM news` |
| `news` 覆盖的标的×日 | 1046 | `SELECT COUNT(DISTINCT symbol, date) FROM news` |
| **覆盖率** | **21.57%** | 上两行相除 |
| `sent-v1` 记录数 | 1046（50 只） | `judgements WHERE prompt_version='sent-v1'` |

也就是说：**接近八成的"标的×日"根本没有新闻，也就没有情绪面判断**。

### 2.2 没有新闻时怎么处理（这是口径的关键）

系统**不把"没有新闻"当成 HOLD**。情绪面在没有新闻的日子**不落库**，即视为**弃权**，而不是投一张
中立的反对票。加权合成时该视角的权重与分母同时剔除：

```
score = Σ_{有记录的视角} w_v·score_v / Σ_{有记录的视角} w_v
```

为什么必须这样：`docs/三分析师预实验诊断.md` 第 98 节记录过旧版的错法——把"缺视角"当 HOLD 参与投票，
结果是 100 个样本里 7 条三视角齐全、投票产出 BUY 0 / SELL 2 / HOLD 98，准确率 0.5 却看着像"有结论"。
弃权与反对必须分开，否则缺数据会伪装成"一致看多"。

### 2.3 情绪面在 12 月窗口的真实覆盖率（本轮新增实测）

2024-12-16 ~ 12-31 这 12 天里：

| 版本 | 记录数 | 覆盖标的 |
| --- | --- | --- |
| `sent-v1` | 41 | **7** |
| `sent-agent-v1` | 61 | 7 |

50 只标的里只有 7 只在 12 月有当日情绪面。**所以这 12 天的"三视角研判"，绝大多数标的实际是
"技术面 + 基本面两视角"**。文档与答辩必须这样表述，不能说成"三视角齐全"。

### 2.4 编排层曾经把这条口径破坏掉（本轮修）

`scripts/orchestrate.py` 原实现里，情绪面用 `date<=?` 的向前填充（ffill）取最近一次记录，
**没有时效上限**。实测后果：

| 项 | 修前 | 修后（`--sent_max_lag 5`） |
| --- | --- | --- |
| 600 条编排记录中有当日情绪面的 | 37（6.2%） | 同 |
| **靠外推旧值** | **563（93.8%）** | 0（超期即视为缺失） |
| 最远外推跨度 | 58 天（11-03 的新闻用于 12-31） | ≤5 天 |
| 编排输出 BUY | 253（42.2%） | 13（2.2%） |
| 编排输出 HOLD | 272（45.3%） | 479（79.8%） |
| 编排输出 SELL | 75（12.5%） | 108（18.0%） |
| 走 LLM 仲裁的条数 | 140 | 37 |

**把 sent 权重置 0 的离线对照**（不改库，仅重算）：`w_sent=0.5` → BUY 57.8%；`w_sent=0.0` → BUY 0.7%。
也就是说修前那 253 条 BUY 几乎全部来自陈旧情绪信号，不是当日研判。

修法是给 ffill 加时效上限：情绪信号的有效期本来就只有几天（验收标准写的是 3–5 天），
超期即视为缺失，当日降级为两视角。**宁缺，不假**。代价是冲突分支从 140 条降到 37 条，
LLM 仲裁样本变少——这是让数字变难看、但让结论成立的那类修正。

修前的 600 条记录留在 `docs/exp_orch_agent_nolag_bak.json`，只作对照，不得用于任何结论。

## 3. 编排层（第三层）到底是什么，不是什么

### 3.1 分支结构

`decide()` 在规则合成之前先判四类分支：

| 分支 | 条件 | 处理 |
| --- | --- | --- |
| `no_tech` | 技术面无记录 | 直接放弃，不产出信号 |
| `unanimous` | 所有有记录的视角同向且非 HOLD | 规则合成，不调 LLM |
| `minor` | 有分歧但存在明显多数（含 HOLD 占多数） | 规则合成，不调 LLM |
| `conflict` | 无法按规则判定 | **调 LLM 仲裁** |

5 天时效后 600 条的实际分布：`unanimous` 314、`minor` 249、`conflict_llm` 37。
37 次智谱 `glm-4-flash` 调用，输入 13,989 / 输出 1,743 tokens，**0 次降级**。

### 3.2 性能上限（必须说清）

- 它**不进入回测信号链**：`docs/exp_orchestrator_agent.json` 的 `note` 与代码注释都写明，
  回测仍读 `fusion-val-v1`。所以编排层对收益**没有贡献**，也不该被算进策略表现。
- `ARB_PROMPT` 现已改为**显式裁决规则表 R1–R5**（2026-11-12 修订，commit `81fe32b`）：
  R1 证据压倒 / R2 技术优先（|score|≥0.05，依据 tech 权重 0.90）/ R3 情绪不翻向
  （增量 ≤0.1，依据情绪面 ACC 0.5054）/ R4 基本面不参与（权重 0）/ R5 证据不足→`REVIEW`。
  模型必须按序匹配并在 `why` 里写明命中的规则编号，所以仲裁结果**可人工复现**：
  给定同样三视角与证据，人能照着规则表推一遍，验证模型选的是不是对的。
- 新增 `REVIEW` 哨兵：模型按 R5 判定证据不足时抛 `_ReviewNeeded`，上层落
  **保守 HOLD + 0 分**并留 `review:` 标记，不退回规则加权硬算方向。
  （退回规则加权会被证伪：实测 2024-12-31 中国移动触发 R5 后，规则加权算出 BUY +0.15，
  与"证据不足"自相矛盾——见 commit `81fe32b` 的修正说明。）
- 规则表不改变"这条链路不进入回测信号链"的事实：`judgements.signal` 仍有
  `CHECK (signal IN ('BUY','SELL','HOLD'))` 约束，REVIEW 无法落库为方向，只在 reason 留痕。
- 它满足"决策 + 工具调用 + 循环"里最弱的一档，**不是**强意义上的多智能体协作。

## 4. 本文件没做的事

- 没有把策略 2、4 从 vote 改成 weighted（改需重跑并重发，属于会覆盖历史结论的动作）；
- 没有补情绪面在 12 月的缺失日期（需再调模型，成本另计）；
- 已给 `ARB_PROMPT` 补显式裁决规则 R1–R5 与 REVIEW 哨兵（commit `81fe32b`），并**在
  2024-12-16~12-31 全 600 条格点上重跑**（版本 `fusion-orch-agent-v1r600b`，
  见 `docs/exp_orch_rule_600b.json`）。实测数据：

  | 版本 | BUY | HOLD | SELL | 走 LLM | LLM 分支内部 |
  |---|---:|---:|---:|---:|---|
  | `fusion-orch-agent-v1`（旧·无规则） | 13 | 479 | 108 | 37 | HOLD 34 / SELL 3 |
  | 规则版 v1（无 P1 校验） | 13 | 459 | 128 | 26 | **SELL 23 / HOLD 3** |
  | 规则版 v2（含 P1 硬校验） | 14 | 474 | 112 | 20 | SELL 7 / HOLD 12 / BUY 1 |

  分支分布（v2）：`unanimous` 314 / `minor` 249 / `conflict_llm` 20 / `review_hold` 17。
  成本：37 次 LLM 调用，33,636 输入 + 2,379 输出 tokens。

- **规则版 v1 有过一次真实误判，已修正**：第一版 R1 允许"证据压倒"但没写死证据来源，
  模型把"PE/PB 分位偏高"当成 R1 的证据，26 条裁决里 23 条判 SELL，直接违反 R4
  "基本面不参与"。修法是加前置约束 P1（估值不构成方向理由）+ 代码硬校验
  （`rule=="R1"` 且 why 含 PE/PB/估值/分位 → 判违规、按 R5 处理）。修正后 LLM 分支
  的 SELL 从 23 降到 7，整体分布回到旧版附近。
  **这条经验值得记住：prompt 里写约束拦不住模型的合理化倾向，必须有代码层校验兜底。**

- **R5 触发率偏高，要如实说**：conflict 共 37 条，其中 17 条（46%）模型判定证据不足
  拒绝裁决、落保守 HOLD。主因是 0.9/0/0.1 权重下技术面 score 常落在 ±0.05 带内（HOLD），
  此时冲突分支确实没有可靠的方向源。这不是 bug，是当前权重结构的真实结果——
  也说明"编排层能解决大部分冲突"这种说法站不住。

- 仍存在的边界：库内 `fusion-orch-agent-v1` 的 600 条是旧的无规则版产物，与
  `v1r600b` 并存；两者**不可混读**，讲"规则版编排层"只能用 `v1r600b` 的数据。
- 没有为 `fusion-val-v1` 补齐 08-08~08-13 的 104 条（`tech-v1` 从 08-14 起才有，回测首 bar 也是 08-14，
  对当前回测无影响；但若将来回测窗口前移到 08-08 就必须先补）；
- 没有做情绪面的时间衰减加权（`w = 0.5**(days/5)`），当前只有"超期丢弃"这一档。
